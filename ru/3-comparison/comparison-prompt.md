# Prompt: сравнение architecture review для Codec API в pgjdbc

Я попросил несколько разных агентов оценить качество и масштабируемость реализации `arraycodec` и публичного Codec API в pgjdbc.

У агентов был доступ к исходному коду. Теперь мне нужно не новое architecture review вместо них, а объективное сравнение их результатов.

## Контекст

Исходная задача для агентов была такой: `../1-review-prompt-creation/design-review-prompt.md`

Ответы агентов:
* `../2-review-execution/fable5.md`
* `../2-review-execution/gpt55.md`
* `../2-review-execution/opus48.md`

## Главная цель

Сравни качество анализа разных моделей и помоги понять:

* где результаты сходятся;
* где различаются;
* какие выводы есть только у одной модели;
* какие выводы подтверждаются текущим кодом;
* какие выводы выглядят неподтверждёнными или галлюцинированными;
* какие важные проблемы из исходной задачи модели пропустили;
* какой из предложенных планов лучше помогает быстро и масштабируемо реализовать `struct` / `array` / Codec API в pgjdbc.

Не торопись с итоговым ответом. Если утверждение модели звучит правдоподобно, но его можно проверить по коду, сначала проверь его. Если данных недостаточно, пометь утверждение как неподтверждённое, а не как ошибку.

## Важное ограничение

Не выполняй исходное architecture review заново как основной результат.

Используй исходную задачу как рубрику для оценки ответов моделей. Новые собственные findings допускаются только в отдельном разделе `Проблемы, пропущенные всеми моделями`, и только если они подтверждаются кодом или явно следуют из JDBC/PostgreSQL API.

## Процедура сравнения

### 1. Извлеки атомарные claims

Сначала разложи каждый ответ модели на отдельные утверждения.

Одно утверждение должно описывать одну конкретную проблему, риск, ограничение или рекомендацию. Не объединяй разные темы в один claim.

Для каждого claim укажи:

* идентификатор claim;
* какая модель его высказала;
* краткую формулировку;
* категорию;
* серьёзность;
* на какие классы, методы, API или сценарии он ссылается;
* есть ли в ответе модели доказательство или это только предположение;
* можно ли проверить claim по текущему коду;
* результат проверки.

Категории:

* public SPI / API boundary;
* type identity и metadata;
* codec registry и lookup;
* scalar codecs;
* array codecs;
* composite / struct codecs;
* domains / enums / ranges / multiranges;
* JDBC compatibility;
* standalone encode/decode;
* performance / allocations / boxing;
* error handling / usability;
* migration от `ArrayEncoding` / `ArrayDecoding`;
* tests / benchmarks;
* maintainability;
* другое.

Серьёзность:

* `blocker` — мешает масштабировать архитектуру или стабилизировать public API;
* `high` — приведёт к заметным correctness/API/performance проблемам;
* `medium` — важный риск, но его можно исправить инкрементально;
* `low` — локальное улучшение, уточнение или polish;
* `nit` — мелкое замечание.

Статус проверки:

* `confirmed` — подтверждается кодом или спецификацией;
* `partially confirmed` — в целом верно, но формулировка слишком широкая или неточная;
* `unclear` — не хватает данных или проверка требует дополнительных экспериментов;
* `false / hallucinated` — противоречит коду или спецификации;
* `design trade-off` — не ошибка, а компромисс с несколькими разумными вариантами;
* `opinion` — вкусовая рекомендация без строгого критерия.

### 2. Проверь существенные claims по коду

Для claims со статусом `blocker`, `high` или влиянием на публичный API обязательно проверь код, если это возможно.

Особенно проверяй утверждения про:

* регистрацию кодеков по OID, имени типа, Java class или schema-qualified name;
* поддержку или отсутствие поддержки `Array`, `Struct`, `SQLData`, `SQLInput`, `SQLOutput`, `CallableStatement`;
* binary/text parity;
* lower bounds, multidimensional arrays, null elements;
* primitive fast path и boxing;
* разделение public API и internal implementation;
* наличие лишних зависимостей public API от `PGStream`, `QueryExecutor`, `Field`, `Tuple`, `ArrayEncoding`, `ArrayDecoding`;
* поведение `ResultSet.getObject(int, Map<String, Class<?>>)`;
* qualified и quoted identifiers;
* cache invalidation для type metadata.

Не называй design trade-off ошибкой, если у PostgreSQL или JDBC нет очевидного универсального решения.

Например, если модель утверждает, что регистрация custom codec по имени типа без схемы ошибочна, проверь альтернативы:

* OID стабилен для built-in типов, но не является переносимым идентификатором пользовательского типа между базами;
* unqualified type name удобнее для пользователя, но может быть неоднозначным;
* schema-qualified registration точнее, но требует от пользователя явной привязки вроде `myschema.my_type -> MyCodec`;
* `search_path` делает resolution context-dependent.

В таких случаях сформулируй компромисс, цену альтернатив и практическую рекомендацию.

### 3. Составь матрицу совпадений

После извлечения claims составь матрицу:

| Claim | Категория | Fable 5 | Opus 4.8 | GPT 5.5 | Проверка по коду | Вердикт |
| --- | --- | --- | --- | --- | --- | --- |
| ... | ... | да/нет | да/нет | да/нет | confirmed / unclear / ... | ... |

Если моделей две, используй только колонки для двух моделей.

### 4. Сгруппируй результаты

Отдельно перечисли:

* подтверждённые проблемы, найденные всеми моделями;
* подтверждённые проблемы, найденные несколькими моделями;
* подтверждённые проблемы, найденные только одной моделью;
* неподтверждённые или сомнительные claims;
* claims, которые выглядят галлюцинациями;
* design trade-offs, которые модели ошибочно могли представить как баги;
* важные темы из исходной задачи, которые модели пропустили.

### 5. Оцени планы моделей

Сравни предложенные план действий не по красоте формулировок, а по практической пригодности для pgjdbc.

Критерии:

* помогает ли план быстро получить работающую реализацию;
* не фиксирует ли преждевременно неудачный public API;
* сохраняет ли путь к primitive fast path без чрезмерного дублирования;
* позволяет ли инкрементально заменить `ArrayEncoding` / `ArrayDecoding`;
* покрывает ли JDBC compatibility, а не только internal codec model;
* учитывает ли custom codecs и сторонние расширения;
* даёт ли понятный порядок работ;
* отделяет ли обязательные архитектурные решения от задач, которые можно отложить;
* не требует ли переписать всю систему до появления первых проверяемых результатов;
* предлагает ли тесты или эксперименты, которые реально снижают риск.

В конце скажи, какой план лучше достигает цели быстрой и масштабируемой реализации `struct` / `array` / Codec API, и почему.

Если лучший результат получается из комбинации планов, собери объединённый план.

### 6. Выдели решения, которые нужно принять до масштабирования

Отдельно перечисли 5-10 решений, которые нужно принять до расширения реализации с `int4` на остальные типы.

Для каждого решения укажи:

* почему оно блокирует или снижает риск масштабирования;
* какие варианты есть;
* какой вариант выглядит предпочтительным сейчас;
* что можно отложить.

Не смешивай эти решения с обычными задачами реализации.

## Формат итогового ответа

Дай результат в такой структуре:

1. `Краткий вердикт`
   * какой ответ модели самый полезный;
   * какой ответ самый доказательный;
   * где модели в основном согласны;
   * где расходятся.

2. `Методика`
   * какие ответы сравнивались;
   * какие части кода проверялись;
   * какие выводы остались без проверки.

3. `Матрица claims`
   * таблица совпадений и статусов проверки.

4. `Подтверждённые общие выводы`
   * проблемы, найденные всеми или несколькими моделями.

5. `Уникальные полезные findings`
   * проблемы, найденные только одной моделью, но подтверждённые кодом или спецификацией.

6. `Сомнительные или ложные claims`
   * неподтверждённые утверждения;
   * галлюцинации;
   * claims, где модель перепутала trade-off с ошибкой.

7. `Пропущенные темы`
   * важные пункты исходной задачи, которые модели не покрыли или покрыли поверхностно.

8. `Сравнение планов`
   * какой план лучше;
   * что взять из каждого плана;
   * что отбросить.

9. `Решения перед масштабированием`
   * 5-10 архитектурных решений, которые нужно принять до расширения реализации на остальные типы.

10. `Рекомендуемый следующий шаг`
    * короткий практический план на ближайшую итерацию.

## Стиль

Пиши на русском. Формулируй выводы технически и проверяемо.

Не используй оценочные фразы вроде «модель глубже понимает задачу», если это не подкреплено конкретными claims и проверкой.

Если claim не проверен, так и скажи. Не превращай предположение в вывод.

Если вывод зависит от политики проекта или будущего public API, отдели факт от рекомендации.
