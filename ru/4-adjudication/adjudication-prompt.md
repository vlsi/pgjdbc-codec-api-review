# Prompt: финальное сравнение двух судебных сравнений architecture review

Я исследую результаты architecture review публичного Codec API для `struct` / `array` / user-defined types в pgjdbc.

У меня есть:

* исходный prompt для первичного architecture review;
* несколько первичных ответов моделей;
* prompt для «судебной процедуры» сравнения этих ответов;
* два независимых результата этой судебной процедуры, полученные разными агентами.

Теперь нужно выполнить финальный adjudication pass: сравнить не первичные ревью напрямую, а два результата сравнения, разрешить расхождения и собрать один consolidated verdict.

Первичные результаты моделей:

Prompt, по которому выполнялась судебная процедура сравнения:

Результаты двух независимых судебных сравнений:

* `<вставить путь к первому результату судебного сравнения>`
* `<вставить путь ко второму результату судебного сравнения>`

Если имена файлов с результатами судебных сравнений уже известны, используй их вместо placeholders выше.

## Нужно ли учитывать prompt судебной процедуры

Да. Используй `../3-comparison/comparison-prompt.md` как методологический контекст.

Он нужен, чтобы понять:

* какие критерии должны были применять агенты;
* какие статусы claims они должны были различать;
* что считалось подтверждённым, неподтверждённым, trade-off или hallucination;
* где результат сравнения мог отклониться от заданной процедуры.

При этом не перепроверяй всю судебную процедуру с нуля. Используй её prompt только как рубрику для оценки качества двух уже полученных сравнений.

## Главная задача

Не выполняй первичное architecture review заново.

Не сравнивай первичные ответы моделей с нуля, если это не нужно для разрешения конкретного расхождения между двумя судебными сравнениями.

Сравни именно два результата судебной процедуры и собери финальный consolidated verdict:

* какие выводы совпали;
* где сравнения расходятся;
* какие расхождения существенны;
* какие расхождения можно разрешить проверкой кода или спецификации;
* какие остаются unresolved;
* какие final claims стоит считать подтверждёнными;
* какие claims стоит считать ложными, галлюцинированными или неподтверждёнными;
* какие решения нужно принять до масштабирования реализации Codec API.

## Процедура

### 1. Извлеки итоговые claims из двух сравнений

Из каждого результата судебного сравнения извлеки:

* confirmed issues;
* partially confirmed issues;
* unresolved / unclear claims;
* false / hallucinated claims;
* design trade-offs;
* пропущенные первичными моделями темы;
* рекомендованные архитектурные решения;
* recommended next steps.

Не смешивай claims разных типов. Если один результат сравнения объединил несколько проблем в один пункт, разложи его на атомарные claims.

### 2. Составь матрицу расхождений

Составь таблицу:

| Тема / claim | Сравнение A | Сравнение B | Совпадают? | Нужно перепроверить? | Финальный вердикт |
| --- | --- | --- | --- | --- | --- |
| ... | ... | ... | да / частично / нет | да / нет | confirmed / false / unresolved / trade-off |

Отдельно отмечай:

* расхождения в самом наличии claim;
* расхождения в severity;
* расхождения в статусе `confirmed` / `unclear` / `false` / `design trade-off`;
* расхождения в рекомендуемом плане работ;
* случаи, где одно сравнение проверило claim по коду, а другое нет.

### 3. Разреши важные расхождения

Для важных расхождений не выбирай сторону по стилю, уверенности или подробности текста.

Если расхождение влияет на public API, архитектурный порядок работ, correctness, JDBC compatibility или performance hot path, попробуй разрешить его:

* проверкой текущего кода;
* проверкой JDBC/PostgreSQL API;
* сверкой с исходным prompt;
* сверкой с prompt судебной процедуры.

Если расхождение нельзя надёжно разрешить без дополнительных экспериментов, пометь его как `unresolved` и сформулируй, какой эксперимент или проверка нужны.

### 4. Не путай ошибки и trade-offs

Не называй design trade-off ошибкой, если у PostgreSQL, JDBC или pgjdbc нет очевидного универсального решения.

Особенно аккуратно оцени claims про:

* регистрацию custom codecs по OID, имени типа, schema-qualified name или Java class;
* влияние `search_path`;
* сохранение domain identity или разворачивание domain в base type;
* quoted identifiers;
* primitive arrays vs boxed arrays;
* public API для offline encode/decode;
* fallback и priority rules для сторонних кодеков;
* binary-only или text-only codecs.

Для таких тем укажи:

* факт по текущему коду или API;
* возможные варианты дизайна;
* цену каждого варианта;
* практическую рекомендацию.

### 5. Проверь, соблюдали ли сравнения процедуру

Коротко оцени качество двух результатов судебного сравнения:

* извлекали ли они атомарные claims;
* проверяли ли существенные claims по коду;
* отделяли ли facts от opinions;
* отличали ли hallucinations от unresolved claims;
* не подменяли ли сравнение новым architecture review;
* давали ли практический next-step plan.

Не превращай этот раздел в оценку «какая модель умнее». Оценивай только пригодность результата.

## Итоговый формат

Дай ответ в такой структуре:

1. `Краткий вердикт`
   * где два судебных сравнения согласны;
   * где расходятся;
   * какой результат сравнения полезнее и почему;
   * насколько финальный verdict надёжен.

2. `Матрица расхождений`
   * таблица claims и финальных статусов.

3. `Финальные confirmed issues`
   * только подтверждённые проблемы;
   * укажи severity и источник подтверждения.

4. `Финальные false / hallucinated claims`
   * claims, которые противоречат коду или спецификации;
   * claims, где модель явно придумала поведение.

5. `Unresolved questions`
   * вопросы, которые не удалось разрешить;
   * какая проверка нужна для каждого вопроса.

6. `Design trade-offs`
   * темы, где нет единственного правильного решения;
   * варианты и рекомендации.

7. `Проблемы, пропущенные обоими сравнениями`
   * добавляй только если это нужно для финального verdict;
   * подтверждай кодом, спецификацией или исходным prompt.

8. `Решения перед масштабированием`
   * 5-10 архитектурных решений, которые нужно принять до расширения реализации с `int4` на остальные типы.

9. `Recommended next iteration`
   * короткий практический план ближайшей итерации.

## Ограничения

* Не делай ещё одно полное architecture review.
* Не пересказывай длинно первичные ответы моделей.
* Не превращай уверенную формулировку в доказательство.
* Если claim не проверен, помечай его как `unresolved` или `unclear`.
* Если вывод зависит от будущей политики публичного API, отделяй факт от рекомендации.
* Пиши на русском, технически и проверяемо.
